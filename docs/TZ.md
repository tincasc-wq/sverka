# ТЗ: Сервис верификации новостей

Oct 12, 2026 · @Tincas

## 1. Цель и границы продукта

«Сверка» (рабочее название) — сервис, который по ссылке или тексту новости за 1–3 минуты выдаёт отчёт: кто первым это опубликовал, кто перепечатал, кто независимо подтвердил или опроверг, и насколько надёжны эти источники.

**Ценность:** человек тратит на проверку новости 20–40 минут ручного поиска. Сервис сокращает это до одного отчёта с объяснением и ссылками.

**Что сервис делает:**

- Извлекает из новости проверяемые утверждения: факты, цифры, цитаты, даты, места.
- Находит публикации на ту же тему в СМИ, Telegram и VK.
- Строит хронологию и цепочку заимствований, определяет вероятный первоисточник.
- Сверяет утверждения между источниками и отмечает расхождения.
- Ведёт реестр источников с рейтингом надёжности, который обновляется по накопленной статистике.
- Выдаёт **индекс подтверждённости** (0–100) с текстовым объяснением.

**Чего сервис НЕ делает (сознательно):**

- Не выносит вердикт «правда / фейк». Формулировки только фактические: «подтверждено N независимыми источниками», «первоисточник анонимен», «опровергнуто официальным заявлением».
- Не проверяет подлинность фото и видео в MVP (это этап 3+).
- Не оценивает мнения, прогнозы и оценочные суждения — только проверяемые факты.
- Не модерирует и не удаляет контент.

## 2. Пользователи и сценарии

В MVP главный пользователь — рядовой читатель в Telegram-боте; редакции и преподаватели подключаются на этапе 2.

| Роль | Задача | Канал | Этап |
| --- | --- | --- | --- |
| Читатель | Быстро понять, стоит ли доверять новости из ленты | Telegram-бот | MVP |
| Журналист / редактор | Найти первоисточник перед перепечаткой, увидеть расхождения в цифрах | Веб-кабинет | 2 |
| Преподаватель / тренер | Разбирать случаи дезинформации на занятиях (связь с CyberFox) | Веб + экспорт отчёта | 2 |
| Аналитик реестра (внутренняя роль) | Размечать источники, разбирать спорные случаи и апелляции | Админка | MVP |
| Внешний сервис | Получать оценку по API | REST API | 3 |

**Ключевые сценарии:**

1. **Проверка по ссылке.** Пользователь пересылает боту ссылку на статью или пост. Бот сразу отвечает «проверяю…», через 1–3 минуты присылает краткий итог и ссылку на полный отчёт.
2. **Пересланный пост.** Пользователь форвардит сообщение из Telegram-канала. Бот берёт текст, канал-источник и время из метаданных форварда.
3. **Произвольный текст.** Пользователь вставляет текст без источника («говорят, что…»). Сервис ищет, где и когда это впервые появилось.
4. **Справка по источнику.** Команда `/source @channel` или домен → карточка источника из реестра: рейтинг, история, аффилированность.
5. **Повторная проверка.** Кнопка «Проверить снова через 6 часов» для свежих событий, по которым подтверждений ещё нет.
6. **Разметка (аналитик).** Аналитик в админке подтверждает или правит выводы системы; эти решения попадают в историю источника и влияют на его рейтинг.

## 3. Функциональные требования

Система состоит из 8 модулей; нумерация требований (ФТ-x.y) используется в задачах и коммитах.

### М1. Приём запроса (Intake)

- **ФТ-1.1** Принимать на вход: URL статьи, URL поста t.me / vk.com, пересланное сообщение Telegram, произвольный текст до 5000 символов.
- **ФТ-1.2** Извлекать текст статьи без меню и рекламы (trafilatura), заголовок, автора, заявленную дату публикации.
- **ФТ-1.3** Нормализовать URL (убирать utm-метки, amp-версии) и возвращать готовый отчёт из кэша, если проверка была менее 6 часов назад.
- **ФТ-1.4** Лимиты: не более 20 проверок в сутки на бесплатного пользователя.

### М2. Извлечение утверждений (Claim Extractor)

- **ФТ-2.1** LLM выделяет 1–7 проверяемых утверждений в структурированном виде (субъект, действие, объект, числа, дата, место, цитата, на кого ссылается).
- **ФТ-2.2** Отделять факты от мнений и прогнозов; мнения помечать как «не проверяется».
- **ФТ-2.3** Формировать 3–5 поисковых запросов на русском и (при необходимости) английском.

### М3. Сбор и поиск (Collector + Search)

- **ФТ-3.1** Фоновый краулер: RSS СМИ раз в 5 минут, Telegram-каналы в реальном времени, VK-сообщества раз в 10 минут.
- **ФТ-3.2** Для каждой публикации сохранять `first_seen_at` — момент, когда краулер её увидел, отдельно от заявленной даты.
- **ФТ-3.3** Сохранять версии текста: если издание правит статью, фиксировать diff (это признак для рейтинга).
- **ФТ-3.4** Поиск по запросу: сначала по собственному архиву (векторный + полнотекстовый), затем через внешнее поисковое API, если найдено менее 5 совпадений.
- **ФТ-3.5** Искать публикации в окне ±72 часа от заявленной даты новости (настраивается).

### М4. Кластеризация и хронология (Story Graph)

- **ФТ-4.1** Объединять найденные публикации в «историю» (одно событие).
- **ФТ-4.2** Внутри истории строить граф заимствований: кто у кого взял (явная ссылка, «по данным …», почти дословное совпадение текста).
- **ФТ-4.3** Определять вероятный первоисточник и считать число **независимых** подтверждений (перепечатки не считаются).

### М5. Сверка (Verifier)

- **ФТ-5.1** Для пары «утверждение — публикация» определять станс: подтверждает / противоречит / уточняет / не касается, с цитатой-обоснованием.
- **ФТ-5.2** Выделять расхождения в числах, датах, именах, цитатах.
- **ФТ-5.3** Отмечать официальные подтверждения и опровержения (сайты ведомств, официальные каналы) отдельным статусом.

### М6. Реестр источников (Source Registry)

- **ФТ-6.1** Карточка источника: тип (СМИ / TG / VK / официальный / агентство), владелец, аффилированность, статус в реестрах Минюста и РКН, возраст, аудитория.
- **ФТ-6.2** Метрики: доля подтвердившихся сообщений, число опровергнутых, статистика правок и удалений, доля первичных публикаций vs перепечаток.
- **ФТ-6.3** Рейтинг 0–100 с доверительным интервалом (мало данных → «недостаточно истории»).
- **ФТ-6.4** История изменений рейтинга с причинами (аудит) и процедура апелляции.

### М7. Отчёт (Report)

- **ФТ-7.1** Краткий итог для бота: индекс, статус, 3 главных факта (до 700 символов).
- **ФТ-7.2** Полный веб-отчёт: утверждения со статусами, лента хронологии, граф заимствований, расхождения, карточки источников, ссылки на все материалы.
- **ФТ-7.3** Каждый вывод в отчёте сопровождается ссылкой на доказательство. Вывод без ссылки не показывается.
- **ФТ-7.4** Кнопки «Сообщить об ошибке» и «Проверить снова позже».

### М8. Админка

- **ФТ-8.1** Управление списками отслеживаемых источников (добавить RSS, TG-канал, VK-сообщество).
- **ФТ-8.2** Очередь спорных случаев и жалоб пользователей, ручная разметка исхода новости (подтвердилась / опровергнута).
- **ФТ-8.3** Дашборд: число проверок, расход токенов и денег, ошибки краулеров.

## 4. Архитектура

Модульный монолит на одном сервере: бот и веб ставят задачи в очередь, воркеры прогоняют их через конвейер, а сборщики независимо от запросов круглосуточно пополняют архив.

Поток проверки: запрос → очередь → 5 шагов конвейера (каждый пишет промежуточный результат в БД, поэтому упавший шаг можно перезапустить) → краткий ответ в бот + ссылка на веб-отчёт. Архив наполняется заранее, поэтому `first_seen_at` надёжен, а поиск по своей базе занимает секунды. Микросервисы не нужны: модули разделены пакетами внутри одного кода и при росте выносятся в отдельные контейнеры.

## 5. Модель данных

Все данные хранятся в одной PostgreSQL 16 с расширениями pgvector (смысловой поиск) и pg\_trgm (нечёткое сравнение текста); отдельная векторная БД в MVP не нужна.

| Таблица | Назначение | Ключевые поля |
| --- | --- | --- |
| `sources` | Реестр источников | id, type (media/tg/vk/official/agency), name, handle\_or\_domain, owner, affiliation, legal\_flags (jsonb: иноагент, блокировка), created\_at, is\_tracked |
| `source_scores` | История рейтинга (append-only) | source\_id, score, ci\_low, ci\_high, n\_observations, reason, computed\_at |
| `documents` | Любая собранная публикация | id, source\_id, url (unique), title, text, lang, published\_at (заявленная), first\_seen\_at (наша), embedding vector(1024), content\_hash, simhash |
| `document_versions` | Правки и удаления | document\_id, text, seen\_at, change\_type (edit/deleted) |
| `stories` | Кластер «одно событие» | id, title, centroid vector, first\_seen\_at, status |
| `story_documents` | Связь история ↔ публикация | story\_id, document\_id, similarity |
| `derivations` | Рёбра графа «кто у кого взял» | from\_doc\_id, to\_doc\_id, kind (explicit\_link/attribution/near\_copy), confidence |
| `checks` | Запрос на проверку | id, user\_id, input\_type, input\_raw, document\_id, story\_id, status (queued/running/done/failed), confirmation\_index, summary, created\_at, finished\_at |
| `claims` | Утверждения из проверяемой новости | id, check\_id, text, structured (jsonb), is\_checkable |
| `claim_evidence` | Результат сверки | claim\_id, document\_id, stance (supports/contradicts/refines/unrelated), quote, discrepancy (jsonb), is\_independent |
| `outcomes` | Итоговый исход истории (для рейтинга) | story\_id, verdict (confirmed/refuted/mixed/unknown), decided\_by (analyst/official/auto), evidence\_url, decided\_at |
| `users` | Пользователи бота и веба | id, tg\_id, role (user/analyst/admin), plan, daily\_quota |
| `feedback` | Жалобы и апелляции | id, check\_id or source\_id, user\_id, text, status, resolution |
| `llm_calls` | Учёт расходов и отладка | check\_id, stage, model, tokens\_in, tokens\_out, cost\_usd, latency\_ms |

**Правила:**

- `first_seen_at` записывается один раз и никогда не меняется — это главное доверенное время системы.
- `source_scores` и `outcomes` только дополняются (аудит, защита при спорах и исках).
- Тексты статей хранятся 90 дней, далее остаются метаданные, хэши и эмбеддинги (авторское право + объём диска).
- Миграции — только через Alembic, никаких ручных ALTER в проде.

## 6. Алгоритмы

Ключевая идея: LLM делает только лингвистические задачи (извлечь, сравнить), а итоговые цифры считает детерминированный код — так результат воспроизводим и объясним.

### 6.1 Извлечение утверждений

- Claude с tool use / JSON-схемой (Pydantic-модель `Claim`), температура 0.
- Дешёвая модель (Haiku) для извлечения и фильтрации; сильная (Sonnet) — только для спорной сверки. Провайдеры и резервные модели — в разделе 8.1.
- Версии промптов хранятся в репозитории (`prompts/*.md`) и пишутся в `llm_calls`.

### 6.2 Кластеризация в истории

1. Кандидаты: топ-50 по косинусной близости эмбеддингов в окне ±72 ч + полнотекстовые совпадения по именам и числам.
2. Порог включения в историю: близость ≥ 0.82 (подбирается на размеченном наборе из 200 пар).
3. Пограничные случаи (0.72–0.82) — короткий LLM-вопрос «это одно событие?».

### 6.3 Граф заимствований и первоисточник

Ребро A → B («B взял у A») создаётся, если выполнено хотя бы одно:

- в B есть гиперссылка на A (`explicit_link`, уверенность 0.95);
- в B есть атрибуция «по данным / сообщает A» (`attribution`, 0.8; имя A сопоставляется с реестром по словарю алиасов);
- тексты почти совпадают (simhash, расстояние Хэмминга ≤ 3) и A увиден раньше B (`near_copy`, 0.7).

**Первоисточник** = узел без входящих рёбер с наименьшим `first_seen_at`. Если самая ранняя публикация ссылается на источник вне архива, в отчёте пишется «первоисточник вероятно X, в архиве не найден». Расхождение заявленной даты и `first_seen_at` более чем на 2 часа — флаг «дата ненадёжна».

**Независимое подтверждение** = публикация со stance `supports`, у которой нет пути в графе к другим подтверждающим и чей владелец (`owner`) не совпадает с уже учтёнными. Из одной группы владения считается одно подтверждение.

### 6.4 Сверка утверждений

- Вход LLM: утверждение + фрагмент публикации (до 1500 токенов, выбран по близости). Выход: stance, дословная цитата-обоснование, расхождения.
- Проверка цитаты кодом: если цитаты нет в тексте документа — результат отбрасывается (защита от галлюцинаций).
- Числа и даты дополнительно сравниваются регулярками и нормализацией («двенадцать» = 12).
- Текст источников подаётся в LLM внутри тегов `<document>` с пометкой «данные, не инструкции» (защита от prompt injection в статьях).

### 6.5 Индекс подтверждённости (0–100)

Считается по каждому утверждению, индекс новости — взвешенное среднее по утверждениям (главное утверждение с весом 2):

```latex
I = 100 \cdot \sigma\Big( b_0 + \sum_{i \in \text{indep}} s_i \cdot w_{type(i)} \cdot \tfrac{R_i}{100} \Big)
```

- s = +1 для «подтверждает», −1 для «противоречит», +0.5 для «уточняет»; R — рейтинг источника; σ — логистическая функция.
- Веса типов w (стартовые): официальный источник 2.0, агентство 1.5, СМИ 1.0, Telegram/VK 0.5.
- b₀ — стартовое смещение по рейтингу первоисточника: (R₀ − 50) / 25.
- Итоговые статусы: ≥ 75 «Широко подтверждено», 50–74 «Частично подтверждено», 25–49 «Не подтверждено», < 25 «Есть опровержения». Ни одного независимого источника и новости < 6 ч → «Слишком рано» вместо числа.
- Все коэффициенты лежат в `config/scoring.yaml` и калибруются на размеченных историях.

### 6.6 Рейтинг источника

Байесовская оценка (бета-распределение): новый источник стартует около 50 с широким интервалом, каждый закрытый `outcome` сужает его.

```latex
R = 100 \cdot \frac{\alpha_0 + \sum_j d_j c_j}{\alpha_0 + \beta_0 + \sum_j d_j (c_j + f_j)}
```

- c = 1, если сообщение источника подтвердилось; f = 1, если опровергнуто; тихая правка факта без пометки = f 0.5.
- d = затухание во времени (полупериод 180 дней): источник может исправиться или испортиться.
- Стартовые α₀, β₀ задаёт аналитик по типу источника (например, агентство 6/2, анонимный TG-канал 2/2).
- При менее чем 10 закрытых исходах в отчёте пишется «недостаточно истории», число не показывается.
- Пересчёт — ночным фоновым заданием, с записью в `source_scores` и причиной изменения.

## 7. Источники данных и интеграции

Основа MVP — собственный архив из RSS и Telegram: он даёт надёжное время публикации и не зависит от платных API. Внешний поиск — добавка для новостей старше архива и неизвестных источников.

| Источник | Как получаем | Объём в MVP | Ограничения | Этап |
| --- | --- | --- | --- | --- |
| RSS СМИ | feedparser + trafilatura для полного текста | \~200 изданий | У части изданий RSS нет → разбор sitemap или главной | MVP |
| Telegram-каналы | Telethon (MTProto) от отдельного служебного аккаунта | \~300 каналов | Нет глобального поиска, только подписки; флуд-лимиты; аккаунт могут заблокировать | MVP |
| Telegram-бот (вход) | aiogram 3, Bot API | — | Форвард даёт канал и дату оригинала | MVP |
| VK | VK API (wall.get, newsfeed.search) | \~100 сообществ | Лимиты запросов на токен | 2 |
| Внешний поиск | Яндекс Search API (Yandex Cloud); резерв — SearXNG на своём сервере | До 5 запросов на проверку | Платно за запрос; тарифы уточнить | MVP |
| Официальные источники | RSS и парсинг сайтов ведомств, их TG-каналы | \~50 | Сайты часто без RSS, часть закрыта для зарубежных IP | MVP |
| Реестры (Минюст — иноагенты, РКН — блокировки) | Периодическая выгрузка | — | Только как фактический флаг, не влияет на рейтинг автоматически | 2 |
| Фактчекинг-базы | Google Fact Check Tools API, проверки русскоязычных фактчекеров | — | Доступность из РФ проверить | 2 |
| X (Twitter) | API | — | Дорого, в РФ заблокирован — не включаем | — |
| Claude API | Адаптер app/llm/: Anthropic SDK + OpenAI-совместимый клиент | — | Claude — зарубежный сервер и оплата; резерв — DeepSeek и Yandex AI Studio (см. 8.1) | MVP |
| Эмбеддинги | Локальная модель `multilingual-e5-large` или `bge-m3` (хорошо работают с русским) | \~20 тыс. документов/сутки | CPU справится, GPU — при росте | MVP |

**Стартовый список источников** составляется вручную в `seeds/sources.yaml` с разными позициями (государственные, независимые, региональные, зарубежные русскоязычные, крупные TG-каналы) — иначе «независимые подтверждения» будут из одного лагеря.

## 8. Стек и инфраструктура

Весь бэкенд — на Python: для вайбкодинга это лучший выбор (лучше всего покрыт библиотеками NLP и парсинга). Принцип — минимум движков: одна БД, один брокер, один сервер.

**Правила:**

- Адаптер `app/llm/` даёт один интерфейс (запрос → проверенный по схеме Pydantic ответ) и две реализации: Anthropic SDK и OpenAI-совместимый клиент (DeepSeek, Yandex AI Studio; совместимость проверить на этапе 1).
- **Автоматический переход на резерв**: ошибка доступа или оплаты, таймаут, отказ модели или дважды невалидный JSON. Провайдер и причина перехода пишутся в `llm_calls`.
- **Отбор по замеру**: каждая модель-кандидат прогоняется на эталонных историях. Метрики: точность stance, доля валидного JSON, доля цитат, найденных в исходном тексте, и ₽ за успешную проверку. Резервные модели перепроверяются раз в месяц.
- **Промпты по провайдерам**: один промпт на шаг; если модели нужна другая формулировка — отдельный файл `prompts/<шаг>.<провайдер>.md`.
- **Фоновые задачи** (повторные проверки, пересчёт после смены промпта) идут в пакетном или асинхронном режиме: у Claude и Яндекса он вдвое дешевле.
- **Дневной потолок расходов** по каждому провайдеру в конфиге; при превышении — оповещение админу и переход на более дешёвую модель.
- **Данные пользователей** в LLM не передаются: только текст новости и публикаций (важно для зарубежных провайдеров и 152-ФЗ).

## 9. Нефункциональные требования, безопасность, право

**Производительность и надёжность**

| Параметр | Цель MVP |
| --- | --- |
| Время первого ответа бота («проверяю…») | < 2 с |
| Полная проверка (p90) | < 3 мин |
| Одновременные проверки | 10 |
| Архив | до 1 млн документов без смены архитектуры |
| Доступность | 99% (допустим простой на обновления) |
| Резервное копирование | pg\_dump ежедневно, хранение 14 дней, копия вне сервера |

Сбой одного источника (поиск, VK, один сайт) не ломает проверку: отчёт строится по тому, что есть, и честно пишет, что источник был недоступен.

**Безопасность**

- Секреты (ключи API, сессия Telethon, токен бота) — только в `.env` на сервере, `.env` в `.gitignore`, в репозитории — `.env.example`.
- Служебный Telegram-аккаунт — отдельный номер, не личный.
- Защита от prompt injection: текст статей — всегда данные, ответы LLM валидируются по схеме, цитаты проверяются на наличие в исходном тексте.
- Защита от SSRF: пользовательские URL не могут вести на внутренние адреса (127.0.0.1, 10.x, 169.254.x и т.п.), таймауты и лимит размера скачивания.
- Админка — за авторизацией через Telegram Login, роли user / analyst / admin.
- Rate limit на бот и API, защита от накрутки жалоб на источники.

**Юридические аспекты (нужна консультация юриста до публичного запуска)**

- **Деловая репутация (ст. 152 ГК РФ).** Никаких ярлыков «фейковое СМИ». В публичной карточке — только проверяемые факты со ссылками и методика расчёта.
- **Публичная методика.** Формулы и критерии опубликованы на сайте; есть процедура апелляции для источников.
- **Авторское право.** В отчёте — только короткие цитаты со ссылкой (ст. 1274 ГК РФ), полные тексты не публикуются.
- **Иноагенты и заблокированные ресурсы.** При цитировании — обязательная маркировка; правила ссылок на заблокированные ресурсы уточнить у юриста.
- **Персональные данные (152-ФЗ).** Храним минимум (Telegram ID); при работе с российскими пользователями — локализация и уведомление РКН, политика конфиденциальности.
- **Дисклеймер** в каждом отчёте: «Автоматический анализ открытых источников, не является утверждением о истинности или ложности».

Строим маленькими вертикальными шагами: каждый этап заканчивается рабочей вещью, которую можно запустить и потрогать. Ориентир — 6–8 недель до MVP при работе по вечерам.

### 10.2 Этапы и критерии приёмки

1. **Каркас (неделя 1).** Репозиторий, Docker Compose (Postgres + Redis + app), модели и первая миграция, CLAUDE.md.
   - Приёмка: `docker compose up` поднимает систему, `/health` отвечает, таблицы созданы, тесты зелёные.
2. **Сборщики (недели 2–3).** RSS + Telegram, запись `first_seen_at`, эмбеддинги, дедупликация.
   - Приёмка: за сутки собрано ≥ 10 тыс. документов, дублей < 1%, падение одного фида не останавливает остальные.
3. **Конвейер проверки в консоли (недели 3–4).** CLI `python -m app.check <url>` → утверждения, история, граф, сверка, индекс в JSON.
   - Приёмка: на 20 эталонных историях первоисточник найден верно в ≥ 70% случаев, нет цитат, которых нет в источнике.
4. **Telegram-бот + веб-отчёт (недели 5–6).** Очередь, краткий ответ, страница отчёта с хронологией и графом.
   - Приёмка: 10 друзей-тестеров проверяют по 5 новостей, p90 < 3 мин, система не падает.
5. **Реестр и админка (недели 6–7).** Карточки источников, разметка исходов, ночной пересчёт рейтинга, жалобы.
   - Приёмка: каждое изменение рейтинга имеет записанную причину; аналитик размечает историю за < 1 мин.
6. **Закрытая бета (неделя 8).** Деплой на VPS, бэкапы, мониторинг, публичная страница методики.
   - Приёмка: неделя работы без ручного вмешательства, расход на LLM в пределах бюджета.

Этап 2 (после MVP): VK, фактчекинг-базы, кабинет редакции на Next.js, экспорт кейсов в CyberFox. Этап 3: публичный API, проверка фото и видео.

### 10.3 Правила работы с Claude

- **Одна сессия — одна задача** из списка ФТ («реализуй ФТ-3.2 и ФТ-3.3»), а не «сделай сборщики» целиком.
- **CLAUDE.md — память проекта**: стек, команды запуска и тестов, соглашения, запреты (не менять схему БД без миграции, не добавлять зависимости без спроса).
- **Git с первого дня.** Коммит после каждой работающей задачи — всегда можно откатиться.
- **Сначала тест, потом код** для алгоритмов (граф, индекс, рейтинг): так видно, что исправление одного не сломало другое.
- **Эталонные истории** (`tests/golden/`) — 20–50 реальных случаев с известным исходом. Их собираете вы (знание предмета), я превращаю их в тесты. Это главная мера качества.
- **Промпты — код.** Изменение промпта = коммит + прогон на эталонных историях.
- **Ревью перед каждым этапом**: `/code-review` и `/security-review` перед деплоем.
- **Вы — владелец решений, я — исполнитель**: список источников, стартовые рейтинги и формулировки отчётов утверждаете вы.

### 12.1 Принципы

- **Независимость.** Оплата не влияет на рейтинги и выводы отчётов. Клиент не может изменить рейтинг своего источника иначе чем через общую процедуру апелляции. - **Не продаём:** рекламу в отчётах, платное повышение рейтинга, «премиальное размещение» в реестре.
- **Экономика.** Себестоимость проверки \~1–2 ₽ (раздел 8.1), постоянные расходы \~12–25 тыс. ₽/мес — бесплатный тариф с лимитом допустим. Для выхода в ноль достаточно одного клиента на тарифе «Редакция».

3. **12+ месяцев.** API и лицензия реестра — когда у реестра накопится история исходов за год.

### 12.4 Требования к системе (М9. Биллинг, этап 2)

- **ФТ-9.1** Тарифы и квоты: таблицы `plans` (лимиты проверок, мест, тем, вызовов API) и `subscriptions` (клиент, тариф, период, статус). Квота проверяется до постановки задачи в очередь.
- **ФТ-9.2** Организации и места: таблица `organizations`, пользователи привязываются к организации с ролями owner / member.
- **ФТ-9.3** Мониторинг тем: таблица `watch_topics` (запрос, ключевые слова, эмбеддинг). Фоновая задача сопоставляет новые истории с темами и шлёт оповещение в Telegram или на e-mail не позднее чем через 1 ч.
- **ФТ-9.4** API-ключи: выпуск и отзыв в кабинете, учёт вызовов, лимиты по тарифу.
- **ФТ-9.5** Оплата: карты РФ через платёжный сервис (ЮKassa или CloudPayments) для Pro; для юрлиц на старте — счёт и акт вручную, в системе только статус подписки.
- **ФТ-9.6** Маржинальность: расходы из `llm_calls` и поискового API привязываются к клиенту; в дашборде — себестоимость и маржа по тарифам.
- **ФТ-9.7** Аудит независимости: изменение рейтинга источника, связанного с платящим клиентом, помечается и требует подтверждения вторым аналитиком.
